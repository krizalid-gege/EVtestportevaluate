# 马来西亚自营 CPO 充电平台——最小演示版设计

- 文档日期：2026-11-20
- 文档状态：已根据对话确认内容整理，等待用户书面评审
- 当前阶段：第一阶段 A——OCPP 充电闭环与模拟结算
- 后续阶段：第一阶段 B——Stripe 测试支付；第二阶段——真实收费前加固

## 1. 项目背景

用户计划以自有品牌充电桩建设并运营海外 CPO 平台，不对接其他充电平台。首个目标国家为马来西亚，泰国和新加坡只作后续扩展预留。

项目由一名不具备前端、后端和架构经验的人员配合 AI 开发，用户负责真实设备操作、账号注册、下载、现场测试和外部协调。因此，方案必须控制组件数量、部署难度及运维成本，并为每个阶段提供可观察的验收结果。

平台最终规划容量为 100 把直流枪和 300 把交流枪；单站最多 20 把直流枪和 60 把交流枪。当前验收不按最终容量执行，只验证最小演示闭环。

## 2. 项目目标

### 2.1 第一阶段 A 目标

在不接 Stripe、不发生真实资金交易的前提下，验证以下链路：

> 插枪 → 用户登录/扫码登录 → 选择充电 → OCPP 授权启动 → 充电状态与电量上报 → 用户或车辆停止 → 生成订单 → 计算电费和服务费 → 生成明确标识的模拟支付记录。

第一阶段 A 同时验证：

- OCPP 模拟器正常充电流程。
- GB/T 直流实桩与实车的正常充电流程。
- 启动失败时不生成充电中订单。
- 后台可查询设备、充电订单、OCPP 事件和模拟支付记录。

### 2.2 第一阶段 B 目标

在第一阶段 A 的充电主链路稳定后，将模拟支付实现替换或并行为 Stripe 测试实现，验证：

- 用户选择预授权档位。
- Stripe 托管页面完成测试预授权。
- 启动失败后取消预授权。
- 充电结束按实际金额确认测试扣款。
- 重复 Webhook 不造成重复处理。
- 管理员执行测试退款。

### 2.3 非目标

第一阶段不构成可公开运营、可真实收费或可承载最终 400 把枪的商业系统验收。

## 4. 范围

### 4.1 第一阶段 A 范围内

1. 用户邮箱注册、验证、登录、退出和密码找回。
2. 用户扫码进入指定充电枪页面。
3. 插枪后启动充电，展示等待、充电中、停止中和已结束状态。
4. 用户主动停止充电。
5. 接收并保存 OCPP 设备、状态、交易和电量数据。
6. 生成充电订单，计算电费、服务费和合计金额。
7. 生成带 `SIMULATED` 标识的模拟支付成功记录。
8. 后台管理站点、单枪直流桩、充电枪、演示价格和二维码。
9. 后台查看设备在线状态、订单、OCPP 事件和模拟支付记录。
10. 管理员、客服、站点人员三类角色及数据权限。
11. 基础站内通知和交易邮件。
12. 云上最低演示环境、每日数据库备份和基础日志。
13. 英文、马来文、中文用户端关键流程文案。

### 4.2 第一阶段 B 范围内

1. Stripe 测试模式和托管银行卡支付页面。
2. 用户选择可配置预授权档位。
3. 预授权、取消、按实确认扣款和退款。
4. Stripe Webhook 验签、幂等和事件保存。
5. 支付失败记录和用户限制的基础实现。
6. Stripe 与平台测试订单对账。

### 4.3 当前范围外

- 真实用户资金、正式商户扣款和公开运营。
- 手机 APP、公众地图找站、预约充电。
- 余额钱包、虚拟余额、保存银行卡。
- 短信登录、WhatsApp 通知。
- 发票、营销、充值活动。
- OCPI、第三方平台、漫游、多运营商分账。
- 家充共享收费、动态负荷均衡、OCPP Smart Charging。
- 双枪同时充电、双枪同时充一辆车。
- OCPP 2.0.1、ISO 15118、Plug & Charge。
- 平台 OTA、批量固件升级。
- Redis、RabbitMQ、Kafka、Kubernetes。
- 400 把枪容量和集中重连验收。

## 6. 技术路线与组件

采用 TypeScript 轻量全栈：

- Next.js：用户 Web/PWA 和运营后台。
- NestJS：业务 API。
- PostgreSQL：业务数据、订单、事件和第一阶段后台任务。
- Prisma：类型安全的数据访问与迁移。
- 独立 Node.js OCPP 进程：WSS/WebSocket 长连接和 OCPP 1.6J 消息。
- Stripe 官方 SDK：仅第一阶段 B 使用。
- Docker Compose：本地开发依赖和演示环境编排。
- GitHub Actions：自动测试和构建。

OCPP 服务独立进程运行，避免 Web/API 发布时主动中断充电连接。第一阶段可与应用部署在同一台云主机，但不得与 Web 进程共用生命周期。

## 7. 总体架构

第一阶段 A 不部署 Stripe Webhook，不创建 Stripe API 密钥，不保存任何银行卡信息。

## 8. 核心流程

### 8.1 第一阶段 A 正常流程

1. 用户将充电枪连接到车辆。
2. 用户扫描枪二维码；未登录时先完成邮箱登录。
3. 系统校验用户、站点、设备、枪和演示价格。
4. 页面显示设备信息、电费单价、服务费单价和“模拟支付”标识。
5. 用户点击开始充电。
6. 系统创建待启动订单和模拟授权记录。
7. OCPP 服务发送 `RemoteStartTransaction`。
8. 只有收到有效 `StartTransaction` 后，订单才进入充电中。
9. 系统保存电表值和充电状态，页面展示当前电量和试算金额。
10. 用户、车辆或设备停止充电。
11. 系统以有效停止交易数据生成最终订单金额。
12. 系统生成 `SIMULATED_SUCCEEDED` 模拟支付记录。
13. 用户可查看订单，后台可核查完整事件链。

### 8.2 第一阶段 B 正常流程

1. 用户插枪、扫码、登录并选择预授权档位。
2. 系统创建订单和 Stripe 手动确认扣款模式的预授权。
3. 用户在 Stripe 托管页面完成测试授权。
4. 浏览器返回只用于跳转；后端通过 Stripe 服务端查询和 Webhook 核实授权。
5. 授权有效后发送远程启动命令。
6. 充电结束后按实际金额确认测试扣款并释放剩余额度。
7. 支付和充电状态分别保存，邮件失败不回滚订单或支付。

### 8.3 达到预授权保护线（第一阶段 B）

当订单试算金额接近预授权额度时，系统通知用户并请求安全停止。若设备离线，平台不能保证远程停止成功；断网续充可能产生超额金额，超额部分不得不经确认直接扣取，应进入人工核查。

## 9. 功能需求（EARS）

### 9.1 账户与访问

- **REQ-ACC-001**：当新用户提交未注册且格式有效的邮箱时，系统应创建未验证账户并发送验证邮件。
- **REQ-ACC-002**：当用户邮箱尚未验证时，系统应允许登录到受限页面，但应阻止启动充电。
- **REQ-ACC-003**：当用户请求重设密码时，系统应发送一次性、有限有效期的重置链接，且不得泄露邮箱是否已注册。
- **REQ-ACC-004**：系统应为账户预留可空手机号字段，但第一阶段不要求短信验证。
- **REQ-ACC-005**：当测试账户被停用时，系统应阻止登录和新充电，同时保留历史订单。

### 9.2 站点与设备

- **REQ-DEV-001**：系统应以“站点—充电桩—充电枪”三层保存设备关系。
- **REQ-DEV-002**：系统应为每个充电桩保存唯一 OCPP 标识，且同一环境内不得重复。
- **REQ-DEV-003**：第一阶段创建直流设备时，系统应限制为单枪和 20kW 演示型号。
- **REQ-DEV-004**：系统应为每把枪生成不可直接推断顺序的二维码标识，扫码后应只显示允许公开的信息。
- **REQ-DEV-005**：当设备离线时，系统应阻止新的远程启动。
- **REQ-DEV-006**：当管理员修改设备或静态功率配置时，系统应保存修改前后值、操作人和原因。
- **REQ-DEV-007**：系统应记录桩端固件版本，但第一阶段不得提供固件升级按钮。

### 9.3 充电与订单

- **REQ-CHG-001**：当用户扫描有效二维码且已插枪时，系统应显示枪状态、演示价格和启动入口。
- **REQ-CHG-002**：当用户重复提交启动请求时，系统应通过幂等键阻止同一枪生成多个有效启动订单。
- **REQ-CHG-003**：当 OCPP 服务仅收到远程启动接受响应、尚未收到开始交易时，系统应保持订单为启动中，不得显示充电中。
- **REQ-CHG-004**：当收到有效 `StartTransaction` 时，系统应将设备交易编号与唯一充电订单关联。
- **REQ-CHG-005**：当收到重复开始或停止交易消息时，系统应返回协议允许的成功响应，但不得重复创建订单或支付记录。
- **REQ-CHG-006**：当充电枪已有活动订单时，系统应拒绝另一用户启动同一枪。
- **REQ-CHG-007**：当用户主动停止时，系统应发送远程停止并显示停止中，直至收到有效停止交易或进入异常处理。
- **REQ-CHG-008**：当收到有效 `StopTransaction` 时，系统应冻结最终计费输入并生成订单金额快照。
- **REQ-CHG-009**：若停止交易长期缺失，则系统应将订单标记为异常并保留人工核查入口，不得自动删除订单。

### 9.4 计费与模拟支付

- **REQ-BIL-001**：系统应分别保存每 kWh 电费单价和每 kWh 服务费单价。
- **REQ-BIL-002**：系统应以订单有效电量分别计算电费和服务费，并保存合计金额。
- **REQ-BIL-003**：系统应以整数 Wh 保存标准化电量，以 MYR 最小货币单位保存金额，禁止使用二进制浮点数直接计算金额。
- **REQ-BIL-004**：系统应以 UTC 保存时间，并以 `Asia/Kuala_Lumpur` 作为马来西亚站点显示时区。
- **REQ-BIL-005**：当管理员修改演示价格时，系统不得改变已创建订单的价格快照。
- **REQ-BIL-006**：当第一阶段 A 订单正常结束时，系统应创建一条且仅一条 `SIMULATED_SUCCEEDED` 支付记录。
- **REQ-BIL-007**：系统应在用户和后台页面明确标识模拟支付，不得将其显示为 Stripe 或真实银行卡扣款。
- **REQ-BIL-008**：第一阶段 A 不得创建账户余额、虚拟钱包或银行卡资料。

### 9.5 后台、权限与通知

- **REQ-ADM-001**：当站点人员查询设备或订单时，系统应只返回其被分配站点的数据。
- **REQ-ADM-002**：当客服请求修改价格、远程控制或退款时，后端应拒绝请求并记录安全审计事件。
- **REQ-ADM-003**：当管理员执行远程控制时，系统应要求二次确认和操作原因。
- **REQ-ADM-004**：当订单完成时，系统应生成站内通知并尝试发送交易邮件；邮件失败不得改变订单状态。
- **REQ-ADM-005**：系统应提供按站点、设备、订单号和测试用户查询 OCPP 事件的能力。
- **REQ-ADM-006**：用户端关键流程应提供英文、马来文和中文资源，后台第一阶段使用中文。

### 9.6 第一阶段 B Stripe

- **REQ-PAY-001**：当用户选择预授权档位时，系统应创建与实际订单唯一关联的 Stripe 测试支付意图。
- **REQ-PAY-002**：系统应验证 Stripe Webhook 签名，不得信任浏览器回传或未经核验的支付状态。
- **REQ-PAY-003**：当收到重复 Stripe 事件时，系统应保证业务处理幂等。
- **REQ-PAY-004**：当设备确认未启动且不存在迟到启动风险时，系统应取消对应预授权。
- **REQ-PAY-005**：当订单正常结束时，系统应按实际订单金额确认测试扣款，不得默认按预授权全额扣款。
- **REQ-PAY-006**：当最终扣款失败时，系统应保留充电订单、记录支付失败并限制用户新充电。
- **REQ-PAY-007**：当管理员退款时，系统应创建独立退款记录并保存原支付、原因、操作人和 Stripe 退款编号。

## 10. 核心数据与不变量

主要实体：

- User、UserCredential、Role、UserSiteAssignment
- Site、Charger、Connector、ConnectorQrCode
- Tariff、TariffSnapshot
- ChargingOrder、ChargingOrderEvent
- OcppConnection、OcppTransaction、OcppMessage、MeterValue
- Payment、PaymentEvent、Refund（第一阶段 B）
- Notification、EmailDelivery
- AuditLog、Alert

必须始终满足：

1. 一把枪在同一时间最多有一个活动充电订单。
2. 一个设备 OCPP 交易编号只归属一个充电订单。
3. 一个订单在第一阶段 A 最多有一个成功模拟支付。
4. 订单金额由订单快照计算，不能读取当前价格重算历史订单。
5. 设备状态、充电状态和支付状态分别保存，不相互覆盖。
6. 原始 OCPP 消息和标准化业务数据均可追溯。
7. 已发生订单、支付和远程控制不得通过后台编辑直接篡改事实。

## 11. 状态划分

### 11.1 充电订单状态

`DRAFT → AUTHORIZING → READY_TO_START → STARTING → CHARGING → STOPPING → SETTLING → COMPLETED`

异常分支：

- `AUTHORIZATION_FAILED`
- `START_FAILED`
- `INTERRUPTED`
- `MANUAL_REVIEW`
- `CANCELLED`

第一阶段 A 的 `AUTHORIZING` 由模拟授权立即完成，不与 Stripe 状态混淆。

### 11.2 支付状态

第一阶段 A：

`SIMULATED_PENDING → SIMULATED_SUCCEEDED`

第一阶段 B 使用独立真实/测试支付状态：

`REQUIRES_ACTION → AUTHORIZED → CAPTURE_PENDING → CAPTURED`

以及 `CANCELLED`、`FAILED`、`REFUND_PENDING`、`PARTIALLY_REFUNDED`、`REFUNDED`。

### 11.3 设备状态

连接状态与枪业务状态分开保存。OCPP 在线不代表枪可用，枪可用也不代表当前允许用户启动。

## 12. 异常处理原则

| 异常 | 第一阶段处理 |
|---|---|
| 用户未登录 | 跳转登录，登录后返回原枪页面 |
| 枪离线或占用 | 阻止启动并展示明确原因 |
| 重复点击启动 | 返回原订单，不重复创建 |
| 远程启动拒绝 | 标记启动失败，模拟授权取消，不生成模拟成功支付 |
| 启动超时 | 进入启动异常；核查设备是否迟到启动 |
| 充电中 Web 重启 | OCPP 进程和订单保持运行 |
| OCPP 消息重复 | 幂等处理，保留必要事件记录 |
| 停止消息缺失 | 进入人工核查，不重复创建订单 |
| 电量或金额异常 | 阻止模拟支付成功，进入人工核查 |
| 邮件失败 | 记录失败并允许重试，不改变订单 |
| 无 CCS2 实车 | 不声明 CCS2 实车验收通过 |

## 13. 非功能要求

### 13.1 安全

- 全站 HTTPS；设备优先 WSS 和每桩独立凭证。
- 密码使用成熟密码哈希算法，不保存明文密码。
- 密钥只存云密钥管理或受保护环境变量，不提交 Git。
- 后端实施接口鉴权、对象级权限、站点数据权限和基础限流。
- 管理操作、远程控制和权限变更写入审计日志。
- 用户订单和支付信息按账户隔离，客服默认查看脱敏信息。

### 13.2 可维护性

- 使用单一 Git 仓库和明确模块边界。
- 每次 AI 修改均形成可审查的 Git 变更。
- 数据库变更通过迁移文件执行，禁止手工修改唯一数据库。
- 配置通过环境变量注入，演示、测试和生产配置分离。
- 不为未来需求提前引入消息队列、微服务或 Kubernetes。

### 13.3 可观测性

- 保存 Web/API、OCPP、后台任务和邮件错误日志。
- 记录设备最后连接、最后心跳和最后有效交易时间。
- 告警至少覆盖设备离线、订单异常和邮件连续失败。
- 日志不得记录完整密码、银行卡、Stripe 密钥或完整访问令牌。

### 13.4 国际化

- 用户端业务文案统一使用翻译资源，不硬编码中文。
- 金额、日期、数字和时区按 locale 展示。
- MYR 金额计算与显示格式分离。
- 后台第一阶段仅中文，但数据库不使用中文作为状态枚举值。

## 14. 部署与备份

### 14.1 第一阶段最低环境

- Windows 11 + WSL2 + Docker Desktop + Git + VS Code。
- 一个云区域，比较新加坡和马来西亚节点后选择。
- 一个轻量容器运行 Web、API 和后台任务。

- HTTPS/WSS、基础日志和邮件告警。
- 本地和云上演示两套环境。

该环境存在单点故障，仅用于最小演示。

### 14.2 后续真实收费推荐环境

- Web/API 至少两个实例，OCPP 至少两个实例。
- 托管高可用 PostgreSQL和时间点恢复。
- 独立预发布与生产环境。
- WAF、外部可用性监控、恢复演练。
- Stripe 正式商户及独立生产密钥。

## 15. 验收标准

### 15.1 第一阶段 A 最小验收

1. 模拟器完成一次正常充电：登录、扫码、启动、电量、停止、订单和模拟支付全部对应。
2. GB/T 实桩和实车完成一次正常充电，平台记录与设备事实可对照。
3. 设备拒绝启动时，订单显示启动失败，不生成模拟支付成功记录。
4. 同一停止交易重复上报时，不产生重复订单或模拟支付。
5. 管理员能查看订单、金额快照、模拟支付和 OCPP 事件。
6. 客服不能修改价格或远程控制，站点人员不能读取其他站点数据。
7. 用户端三种语言的关键流程无直接写死的中文系统提示。
8. 云上环境可从备份完成一次数据库恢复验证。

### 15.2 第一阶段 B 最小验收

1. Stripe 测试预授权成功并启动充电。
2. 启动失败后取消测试预授权。
3. 正常结束按实际金额确认测试扣款。
4. 重复 Webhook 不重复确认扣款或退款。
5. 扣款失败被记录并限制测试用户新充电。
6. 管理员完成一笔测试退款，平台与 Stripe 金额可核对。

### 15.3 真实收费前的独立门槛

- 马来西亚经营主体、Stripe 正式商户和银行结算账户就绪。
- 马来西亚站点、网络、车辆和现场人员落实。
- CCS2 实车测试通过。
- 全耀 WSS、离线缓存补传和安全能力确认。
- 断网续充、支付失败、桩断电和 Web 重启测试补齐。
- 税务、隐私、服务条款和退款文本确认。
- 高可用、数据库恢复和监控告警验收。
- 支付与权限专项审查通过。
- 400 把枪扩展前另做容量与集中重连测试。
